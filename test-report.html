3.1 Self-tests and end-to-end demo

The suite runs the entire product against an in-memory adapter, so a pass demonstrates that the engine carries no coupling to any real application. 24 of 24 checks passed. The bundled demo, which runs against a fake app containing a deliberately planted row-level-security defect, found that defect and exited non-zero as designed.

3.2 Production safety guard

Populace was pointed deliberately at Buzz Buzz's live production backend to confirm it refuses. It stopped before loading the adapter:

✖ REFUSING TO RUN
  The target matches a host listed in neverRunAgainst:
    https://ypdaetbeexyepswyhbui.supabase.co
  Simulated people must never be visible to real users.   exit 1

This is the safety property the product is sold on, demonstrated against the real host rather than asserted.

4 · The check that did not complete

A live simulation of six drivers across Manila and Mumbai was attempted twice and abandoned both times.

Cause. Measured on the test machine: Node lost approximately half of all new TLS connections, each failing at a ten-second connect timeout, sequential and concurrent alike, while curl succeeded four times in five. The link is NAT64 and drops connections in bursts. In practice five of six drivers failed to register and the survivor advanced one simulation tick every forty-five seconds.

Decision. The runs were discarded. Figures from them would describe the office connection, not the product, and publishing them would be worse than publishing nothing. The result of 9 August 2026 — five defects found in three and a half minutes, then no failures across 400 API calls — remains the standing measurement, and it was taken on a sound connection.

Incident: eight simulated accounts left behind

The first attempt was terminated mid-run by an operator timeout, stranding its accounts in the test project. This is the documented failure mode for an interrupted run. Recovery was performed and the project is a disposable test instance holding no real data; no production system was involved at any point.

5 · Defect found in our own tooling

POP-001 · clean reported a false all-clear · Severity: high · Fixed

What happened. The cleanup loop caught every error and counted it as an account that no longer existed. A network failure therefore produced the message "0 removed, 8 not found (already gone)" while the accounts were still present — proved by a direct password sign-in that succeeded moments later.

Why it matters. clean is the mechanism that removes invented people from a customer's database. A false all-clear there is the precise failure this product exists to prevent, and it sat on the safety path.

Fix. Transport failures are now separated from genuine absences, listed by name, and the command exits non-zero so neither a human nor a CI job is told the environment is clear when it was never checked.

5.1 A second, related defect

Investigating the first exposed a second: clean reached each account through createUser, which signs up when an identity is absent. Cleaning an already-clean environment therefore created every identity and deleted it again — writing to a customer's authentication table purely to prove that table was empty, and making the per-account result useless as evidence of what had been stranded.

An optional cleanup capability, signIn, now lets an adapter answer "does this identity exist?" without creating it. It is deliberately not a fourteenth contract method: coverage measures how much of a customer's application a run exercises, and a cleanup-only capability does not belong in that denominator. The published thirteen-method contract is unchanged. Four self-tests cover both an adapter that implements the capability and one that does not.

A candour note. During this investigation the author briefly cited the cleanup output as proof the first defect was real; it was not proof, because the command may have created the very accounts it reported removing. The sound evidence was the direct sign-in probe. The claim was withdrawn and the misleading wording removed. It is recorded here because a report that hides its own corrections is the kind of report this company does not write.

6 · Conclusion

  • Buzz Buzz builds cleanly, its schema applies in full to a fresh environment, and its access controls hold against an anonymous caller holding the shipped key.
  • Populace passes its full suite, finds a planted defect end to end, and refuses a production target when instructed to attack one.
  • One live check remains outstanding. It is blocked on network conditions, not on either product, and the procedure to complete it is recorded.
  • One defect was found and fixed in Populace, in the code that protects a customer's environment — found precisely because the tool was pointed at a real one.
